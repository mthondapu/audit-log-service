# Performance measurements (NFR-3)

NFR-3 requires append, query, pagination, full-chain verification, retention, redaction, and export performance to be measured and documented for the prototype. It sets no targets, so this document reports **observed results only**: there are no thresholds and no pass/fail judgments. The numbers describe one developer machine and are not capacity claims.

## Method

- **Tool.** `scripts/benchmark.py` (Phase 12 decisions P1 to P3), a standard-library script outside the test suite. It calls the same application functions the routes and CLIs use, against a real, throwaway PostgreSQL database per chain size, and times them from outside; production code has no timing hooks. A second, smaller sample drives a real `uvicorn` process over HTTP.
- **Data.** Each chain is seeded as a correctly sealed chain by a benchmark-only bulk insert (the integrity library seals every record, so it verifies exactly like an appended chain). Seeded records are Scenario C access events with five scalar payload values; `actorId` cycles through 100 actors (`actor-0` selects 1%) and `resourceId` through 10 accounts (`acct-0` selects 10%). The first half of the chain has old `recordedAt` values, eligible for a 30-day retention window. Appends are always measured through the real append path (validation, the serialized append, and the stored view). Before the verification steps, the append measurements add 520 typical and 140 large (200-value) events (warm-up included), so verification covers the seeded size plus 660 records (`records verified` below); redactions, exports, and the concurrency appends come after verification.
- **Repetitions.** Per-request operations: 20 warm-up iterations discarded, then 200 measured (500 for typical appends, 100 for redactions); reported as p50, p95, p99, and max in milliseconds (nearest-rank percentiles). Heavy operations: 1 warm-up and 5 measured runs; reported as the median, with min and max. Peak Python memory is measured in a separate run with `tracemalloc`.
- **Environment.** Windows 11 (build 26200), Intel CPU, 8 logical processors; Python 3.13.15; PostgreSQL 18.6 in a local Docker container (`postgres:18`, default settings); the benchmark, the database, and (for the HTTP sample) `uvicorn` on the same machine; commit `6683626`. Measured on 2026-09-29 (UTC).

## Scope of this run

**The final benchmark evidence covers chains of 1,000 and 10,000 records only**, with complete results in every category. The approved matrix also listed 50,000 records, and 100,000 "if feasible"; **no 50,000- or 100,000-record results are part of this evidence**, and no number in this document is estimated or extrapolated from them.

How the final scope came about:

- an earlier run of the whole matrix kept no results: it stopped at the optional 100,000-record stage because the benchmark script's own 10% export scope also selected the export events it had just appended, reaching the configured 10,000-record export limit (which the service correctly refused), and that version of the script saved results only at the end. The script was corrected (the 10% scope now names the resource type, and results are saved after every section);
- the corrected run was stopped by developer decision after the 10,000-record size, and the benchmark scope was finalized at 1,000 and 10,000 records;
- the retention runs with 10,000-value batches and the HTTP sample were measured at 10,000 records in a separate short run (`--sizes --extended --retention-large-batch 10000 --http-size 10000`).

These were decisions about benchmarking time and a benchmark-script error, not application failures.

Raw results: `local/benchmark-results.json` and `local/benchmark-supplement.json` (gitignored; regenerated by the commands in [Reproducing](#reproducing)).

## Observations

These are observations of the measured data; causes are stated only where the evidence supports them.

1. **Serialized appends.** Throughput stays roughly flat as writers are added (about 40 to 51 appends/s at 10,000 records; 19 to 29 at 1,000) while latency rises with the number of writers, as expected from the single append lock (ADR-0003). No run hit the 5-second lock timeout, and every chain was intact afterwards.
2. **Per-request latency grows with chain size.** From 1,000 to 10,000 records, typical-append p50 rose from 15.9 to 39.5 ms, get-by-id p50 from 5.0 to 19.7 ms, and query p50 from about 6 to 11 ms to about 29 to 45 ms. `EXPLAIN ANALYZE` on a seeded 10,000-record chain shows two lookups that every read and every append performs, the archived boundary (latest retention event) and the redacted paths (redaction events naming the records), running as **sequential scans of `audit_records` filtered by `event_type`** (about 4 and 5 ms each at 10,000 records). The schema has only the primary-key and uniqueness indexes. The filters in this benchmark are dense (1% and 10%), and their plans walk the `sequence` index; a sparse filter was not measured.
3. **Full-chain verification dominates checkpoints and exports.** Verification processed about 350 to 900 records/s; creating a checkpoint and every export take about as long as a verification of the whole chain, because each verifies the chain before signing (FR-4, FR-7). At 10,000 records an export took 6 to 11 s regardless of how few records it contained. Peak Python memory for verification and export was 444 to 544 MiB at these sizes; the chain is loaded into memory (Phase 7).
4. **Offline verification is fast.** It checks only the exported records and the signature: about 1,000 to 3,600 records/s, with peak memory under 6 MiB.
5. **Payload size matters.** Large (200-value) events append about 4 times slower than typical ones, and redacting 10 values costs about 2.5 to 5 times one value, consistent with per-value commitments, rows, and purges.
6. **Retention is fast and bounded.** Purging ran at about 9,000 to 83,000 values/s; larger batches mean fewer runs.
7. **Variance.** Some results are not monotonic in chain size (for example, the 1,000-record exports took longer than the 10,000-record 10% export, and verification with a checkpoint was faster than without at 10,000 records). The min-to-max ranges show run-to-run variance on a shared developer machine; these differences were not investigated further, and no conclusion is drawn from them.
8. **HTTP overhead.** Through a real `uvicorn` process, an append and a query each took about 40 ms (p50) at 10,000 records, close to the in-process measurements.

## Index recommendation (not implemented)

Per decision P9, no index was added. Based on observation 2, a behavior-neutral migration 0003 could be **proposed** for review:

- an index on `audit_records (event_type, sequence)`, which targets the two sequential scans that every read and append performs (the archived-boundary and redacted-paths lookups); and, if sparse filters matter in practice,
- indexes on `actor_id`, `resource_id`, `(resource_type, resource_id)`, and `recorded_at` for the FR-2 filters and export selection.

Before any such change, its effect should be measured with the same script (before and after, at the same sizes), because the per-request cost also includes Python work and database round trips. Verification, checkpoint, and export time is dominated by full-chain verification in Python and would not be changed by indexes.

## Reproducing

```sh
export AUDIT_LOG_BENCHMARK_SERVER_URL="postgresql+psycopg://postgres@127.0.0.1:55432/postgres"   # a disposable server
uv run python scripts/benchmark.py --output local/benchmark-results.json
uv run python scripts/benchmark.py --quick --sizes 40 --retention-large-batch 40 --http-size 40 --output local/benchmark-smoke.json   # a quick smoke run
```

The script's defaults are the finalized scope reported here: chains of 1,000 and 10,000 records, retention with 10,000-value batches at 10,000 records, and the HTTP sample at 10,000 records. The reported numbers came from two invocations covering the same sections (see [Scope of this run](#scope-of-this-run)); one default run measures all of them. Larger sizes can be requested explicitly, but none are part of the reported evidence.
